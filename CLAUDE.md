# CLAUDE.md

Qust is a small native desktop player for HTTP audio streams (Icecast / SHOUTcast v2). The user saves up to six streams on "cartridge" cards, plus a playlist of local files and URLs in a drawer under the player, and plays one at a time, with a pixel spectrum analyzer. Everything is Rust: its own engine connects, decodes (Symphonia), mixes and plays to the output device and computes the analyzer, and the windows are drawn with [GPUI](https://gpui.rs) (Zed's UI framework, GPU-rendered: DirectX on Windows, Metal on macOS). The UI imitates Windows 11 (Fluent): a solid background, system light/dark theme, the user's accent color, and native menus and tooltips. Targets Windows and macOS. It was an Electron + Bootstrap app until November 2026, then a Tauri app (webview pages over a Rust core) until 1.1.5; 1.2.0 is the first GPUI version, and it updates Tauri installs in place.

## Commands

```sh
cargo run -p qust-app                       # debug build and run (target/debug/qust.exe)
cargo build --release -p qust-app           # release build (target/release/qust.exe)
cargo build --profile measure -p qust-app   # release build that never hands over to an installed Qust (see Gotchas)
cargo test --workspace                      # all tests: headless, on a silent output, no network
node packaging/windows/build-installer.mjs --exe target/release/qust.exe --version 1.2.0   # NSIS installer into build/bin/
```

You need Rust (stable, via rustup), plus on Windows the MSVC build tools and the Windows SDK (GPUI compiles its shaders with `fxc.exe`, and the resources need `rc.exe`), or on macOS Xcode (GPUI compiles Metal shaders). Node.js only runs the packaging scripts and the reference tooling; there is no npm project and no JS in the app. A running `qust.exe` locks the file, so close it before building.

The app takes `--null-output` (play silently), `--settings <file>` (another settings file instead of the real one), `--background` (tray only, what the startup entry runs) and `--toggle` (Play / Stop, handed to the running Qust). The rest (`--play`, `--play-tone`, `--measure`, `--hidden`, `--offscreen`, `--keep-running`, `--scenario`, `--report`) is for tests and measurements: see `crates/app/src/config.rs`.

**Tests.** `cargo test --workspace` runs the crates' unit and integration tests, the player's end-to-end tests (`crates/player/src/tests.rs`), the windows' behaviour tests and the whole app's end-to-end test (`crates/app/tests/end_to_end.rs`). They need no sound device, no network and no screen: the engine runs on `OutputKind::Null` (a thread that consumes the mix in real time), files are WAVs written to the temp dir, streams come from a small HTTP server inside the test on 127.0.0.1, the store is a temporary file, and windows are hidden and drawn by hand (`qust_ui::capture`). They never open a native menu, picker or message box (tests answer them through `Hooks`). They play in real time, so they take a while. On Windows the Media Foundation tests in `qust-codecs` need the system AAC decoder. One timing test is ignored by default: `cargo test -p qust-spectrum --release --test cost -- --ignored --nocapture`. CI doesn't run the tests.

**Examples**, for checking real streams and files without the app (with a URL they use the network):

```sh
cargo run -p qust-audio --example probe -- [--device] [--quiet] SECONDS ACTION...
cargo run -p qust-codecs --example decode -- <file or URL> [seconds] [--repeat N] [--raw out.f32]
cargo run -p qust-app --example test_stream -- [--name <station>] [--title <ICY title>]   # a local live stream
```

- `probe` drives the engine: on the Null output, or with `--device` on the real device at volume 0. It prints events, every loaded key's status each second, the tap, and `info()` at the end. Each action is `TIME=VERB,KEY[,ARG]`: `0=load,a,<URL or path>` (`URL@START` for a start position), `0=level,a,1`, `3=pause,a`, `5=resume,a`, `6=seek,a,30`, `9=unload,a`, `9=unloadall,-`, `2=volume,-,0.5`.
- `decode` decodes through `qust_codecs::registry()` into memory (never to a device) and reports the codec, output rate and channels, frames decoded against what the packets account for, peak and RMS, and the share of energy above 11 kHz (near zero for HE-AAC decoded as plain LC). `--repeat N` decodes N times with fresh decoders, to check memory stays flat. `--raw` writes interleaved f32 to compare against a reference decoder.
- Capture examples render windows off-screen into PNGs and compare them with the reference renders: `qust-ui` `capture`, `qust-ui-player` `player_capture`, `qust-ui-playlist` `playlist_capture`, `qust-ui-panels` `panels_capture`, `qust-app` `app_capture`, `qust-text` `text-capture`, `qust-fluent` `gallery`. Example names must differ across packages: they share `target/`.

## How it works

**Threads.** GPUI's main thread (the process's first) runs every window, every model, the bridge's UI task and the app; nothing blocks it except quitting (the player's pending saves, at most 2 s). The shell thread (`qust_shell::NativeThread`, a plain Win32 message loop) owns the global shortcuts, the tray icon and its menu, the single-instance window and system appearance changes; its events reach the main thread through `gpui_glue::forward_events` and become requests in `background::route`. The player has its own thread (and the engine its threads), and the bridge a command thread. The file picker, update checks and installs, and the drawer animation's timer run on short-lived threads.

**Start-up** (`app::run`): the launch (`Launch::from_env`), the settings store, `Shell::start` (the single-instance lock first: a second launch hands its arguments over and exits), then GPUI, headless when there is nothing to show (the helper's launch at sign-in: tray only), then `qust_ui::init` (GPUI Kit, the elements, grayscale text), the AppUserModelID, the bridge (the player starts), the theme, the store watcher, the shortcut and updater listeners, the shell's events, and the start-up request (usually: open the player window, which attaches).

**Windows.** The player is 860×267 and not resizable. The playlist drawer adds 320 px (587 in all): the window's content is always 860×587, and opening or closing the drawer only grows or shrinks the window (`qust_shell::drawer`, 14 steps over about 200 ms, moving the window up when it would leave the work area), so the layout never depends on the window height. Settings (520×850) and Stream information (580×590) are separate windows (`panels::open`), owned by the player (above it, no taskbar button, minimized with it), opened hidden, centered over it and kept on its monitor, then shown; Esc closes them, and an open one is brought to the front instead of opening a second. Their title bars follow the app's theme (`window::follow_theme`).

**The UI layer (`qust-ui`).**
- **Bridge.** `qust_ui::UiHost` is the player's `Host`: on the player thread it parses each event (the event names and JSON payloads the pages used to get) into a typed `Event` and sends it down a channel; a task on the UI thread applies them in order to the `Models`. Analyzer frames go into a slot that coalesces (the newest wins, the final blank frame is never lost) and wake the UI only when not already woken. `Player` (cheap to clone) queues every command on one command thread, so the UI never waits; a command with an answer returns a `Reply` that resolves on the UI thread after every event the command caused has been applied. Attaching returns the snapshot after the events it caused; events that arrive earlier are held back and applied after it.
- **Models.** `Models` holds one entity per part (`deck`, `clock`, `seek`, `levels`, `analyzer`, `snapshot`, `playlist`, `status`, `settings`, `shortcuts`, `update`, `background`…), each notified only when its own part changed, so a view observes only what it shows.
- **WindowRoot and live layers.** GPUI re-renders the root view and every dirty view on each frame, and a view that notifies dirties all its ancestors. So every window's root (`WindowRoot`) renders the background, the content view (cached), then **live layers** (the analyzer at 60 Hz, the clock, the title marquee, the seek row, the playing cartridge's badge, the drawer and its equalizer), each drawn at the bounds of a `portal_slot` the content left for it, then overlays (the dialog, a drag ghost). Live layers are siblings of the content: when one changes, the content isn't re-rendered. Live layers have no mouse handlers; clicks and tooltips fall through to the content.
- **The look.** `qust-fluent` rebuilds style.css: the tokens (dark and light), the elements value for value, Chromium's easing curves and CSS transition rules, its focus-visible rule, letter spacing, ellipsis and baseline rounding where GPUI differs (`text.rs`), the pages' icons, and native Win32 tooltips (the control WebView2 used). Text is drawn with grayscale antialiasing.

**Theme.** `theme` in the store is `system` / `light` / `dark`. `qust_ui::theme::apply` installs the `qust_fluent::Theme` global (palette, accent), which every view reads; following the system, the shell reports appearance and accent changes (`WM_SETTINGCHANGE` "ImmersiveColorSet") and the theme is re-applied. The accent comes from the Windows `AccentPalette` registry value (`qust_player::accent`: `base` / `light` / `dark`; the light shade is used in dark mode and vice versa).

**The engine (`qust-audio`).** `Engine::new(Config { codecs, output, user_agent }, on_event)`, then `load(key, Source::Url | Source::File, start_at)`, `unload`, `unload_all`, `keys`, `status`, `set_level` (0 or 1, reached with a ~15 ms fade), `set_paused`, `seek` (files only), `set_volume`, `set_balance` (Web Audio's `StereoPannerNode` law) and `tap()`. Keys are opaque to the engine. `load` replaces a stream already under the key with a fresh connection, and every load gets a new `StreamId`. A new stream has level 0 and is consumed in real time as soon as it has audio.
- **Per stream** (`decode.rs`, a thread of its own): the source, a Symphonia probe (hinted by the Content-Type and the extension), a decoder from `config.codecs`, stereo f32 (mono on both sides, surround with Web Audio's downmix), resampled to the mixing rate (rubato FFT), then a lock-free ring (`ring.rs`) that the mixer drains. A full ring blocks the thread, so the network backs up as it would in a browser. The ring holds 8 s for URLs (`STREAM_SECONDS`: the burst a server sends on connect is what rides out later hiccups) and 3 s for local files (`FILE_SECONDS`). A live stream skips bad packets, and gives up on an I/O error, an unsupported format, or 100 failed packets in a row (`MAX_ERRORS`). A chained Ogg stream (a new logical stream per track, common on Icecast) gets a new decoder at each change.
- **HTTP source** (`source.rs`): it sends `Icy-MetaData: 1`, strips the ICY metadata from the audio and records the title, with 10 s connect and 30 s read timeouts. A response with `Content-Length` and no `icy-metaint` is a file: it has a duration, and with `Accept-Ranges: bytes` it can seek, with a new `Range` request (forward jumps up to 256 KB read through the current connection, and the first 256 KB are kept for the demuxer's probing). Local files seek exactly, HTTP files by the byte estimate. A file cut short is a failure (so the player reconnects), while a live server closing is the stream's end. Ogg streams carry titles as Vorbis comments, which count when there are no ICY titles. SHOUTcast v1 `ICY 200 OK` responses aren't valid HTTP for `ureq` and fail.
- **Mixer** (`mixer.rs`, run in the output callback: no waiting locks, no allocation): sums every stream that has audio and isn't paused, at its level, writes the sum to the `Tap` (before volume, overs kept), then applies volume and balance (smoothed over 5 ms) and clamps. Streams at level 0 are consumed all the same, so they stay at the live point. That is instant switch. A stream starts once 150 ms is buffered. After running out (`Waiting`) it resumes at 0.5 s buffered, twice that after each further stall up to 2 s, and back to 0.5 s after 30 s without one, so a stream arriving barely in real time settles instead of flapping. Pausing fades out over 15 ms, then stops consuming. An unloaded stream fades out for 40 ms before the mixer lets go of it.
- **Output** (`output.rs`): the default device through cpal, in its own format. Stereo goes to the first two channels, and mono devices get the average. The mixing rate is the default device's rate when the engine starts (48 kHz without one, and on `OutputKind::Null`). A device at another rate gets the mix resampled in the callback. The output opens when the first stream loads and closes 3 s after the last one goes (`IDLE_CLOSE`), so it doesn't hold the device or keep the PC awake. While open, it checks every second whether the default device moved, and reopens on the current default when it did or the stream errored, keeping the streams, retrying every second while there is no device.
- **Events**, from one thread (`qust-events`, every 20 ms), with no engine lock held, so the handler may call back in. Per stream: `Duration` first (`None` for a live stream), then `Playing` / `Waiting` alternating, then one `Ended` or `Failed`. Only the stream currently under the key reports. `Failed` before any audio comes at once, and after audio once the buffered audio has played. A seek clears the end, and a file stays open after `Ended`, so seeking back plays it again.
- **`Status`:** `started`, `live` (being consumed now: not paused, waiting, refilling after a seek, or done), `paused`, `ended`, `failed`, `position` (a file's play head, showing a pending seek target at once; for a stream, the same as `played`), `played` (seconds consumed since the load, muted time included, paused time not), `duration` (`Some` only for a file of known length) and `buffered` (seconds ahead of the play head).
- **`info(key)`** (`info.rs`): the details by key, kept across reconnects of the key. The JSON fields are `name`, `title`, `genre`, `description`, `website`, `server`, `contentType`, `format`, `bitrate`, `rate` (measured, from a baseline 5 s in), `samplerate`, `channels`, `metaint`, `size`, `bytes`, `metaBytes`, `titleChanges`, `reconnects` (loads after the first) and `connectedSeconds`. Format, sample rate and channels come from the headers (`icy-br`, `icy-sr`, `ice-audio-info` or `icy-audio-info`), then from the first MP3/ADTS frame header (after any ID3v2 tag), then from the decoder, which fills only what is still unknown (its codec name replaces a format guessed from the content type). An ADTS AAC-LC header at 24 kHz or less is taken as HE-AAC (implicit SBR): the header has the core rate, and playback is at twice that. A local file is described from its MP3/AAC frame, FLAC STREAMINFO or WAV header. A file with no bitrate gets its average from size and duration.
- `icecast_title(url)` reads the title from the server's `status-json.xsl` (blocking, 10 s). `probe_duration(path)` gives a local file's duration without decoding it (`Err` when it can't be opened or isn't audio).

**Formats.** Containers are Symphonia's (MP3 / ADTS, MP4 / M4A, Ogg, Matroska / WebM, FLAC, WAV). Decoders come from `qust_codecs::registry()`:
- MP1, MP2, MP3, FLAC, Vorbis, PCM, ADPCM, ALAC: Symphonia.
- Opus (Ogg, WebM, MP4): `OpusDecoder` (`opus.rs`), a wrapper around the pure-Rust `opus1` crate. Mono and stereo only (surround is refused), always 48 kHz.
- AAC on Windows: `MfAacDecoder` (`mf.rs`, short name `aac-mf`), the system's Media Foundation decoder, for AAC-LC, HE-AAC v1 (SBR) and v2 (PS), from ADTS and MP4. It is registered at `Tier::Preferred`, above Symphonia's, and falls back to Symphonia's AAC-LC by itself when the system has no AAC decoder (Windows N without the Media Feature Pack) or it won't take the stream.
- AAC elsewhere (macOS): Symphonia's AAC-LC.

Files the app accepts have one of the extensions `mp3 m4a aac mp4 ogg oga opus flac wav webm weba`. Streams play whatever their URL.

**Persistence.** Store keys (the same as every earlier version's, so settings carry over):
- `player1-title` / `player1-url` through `player6-*`: the cartridges
- `last-selected-player` / `-title` / `-url`: the last cartridge played
- `last-selected-player` is `playlist` when a playlist entry was last selected, and `playlist-index` is its position
- `playlist`: an array of `{ title, path, duration }` (local file) or `{ title, url, duration }`, and `playlist-open` (the drawer)
- `volume`, `balance`
- `theme`, `visualizer-colors` (`classic` / `white` / `accent` / `off`; clicking the analyzer display cycles them), `autoplay`, `background`, `instant-switch`, `reconnect-minutes` (default 5, 0 = never give up)
- `shortcut-play`, `shortcut-stop`, `shortcut-toggle` (empty string = no shortcut)
- `auto-update`, `update-last-check`

The player writes its own keys. Volume and balance are saved 300 ms after the last change, the playlist 400 ms, and what is pending is written when the player window closes. Settings writes its keys through `Player::write_setting`, and the store tells the player at once when `visualizer-colors`, `reconnect-minutes` or `autoplay` is written (`Store::watch`, installed by the app; the player's own writes don't trigger it). The first run imports the Electron version's `<config dir>/qust/config.json`.

**The player.** One thread (`qust-player`) owns everything: `Core` in `machine.rs`, a port of the old page's player with the same function names where they still exist (`active`, `current`, `sync_streams`, `play`, `pause`, `stop`, `lost`, `reconnect`, `watch`), the same constants and the same store keys. It takes messages: commands (`Player::call` runs a closure on the core and answers once the events it caused have gone out, `Player::cast` doesn't wait), engine events, and its own timers (`next_deadline` / `timers`). After every message, `refresh()` emits what changed. `qust-player` doesn't know the UI: it sees a `Host` (events to the windows: `qust_ui::UiHost`), the `Store` and the frame sink. The engine starts when the player window attaches (`attach`) and is dropped when the player window closes (`Player::detach`).

**Player state.** `State` is `stopped` / `connecting` / `playing` / `buffering` / `paused`. `set_state()` sets it and tells the visualizer. `refresh()` sends `player-state` when anything but the clock changed, and every 250 ms while not stopped. It sends `player-status` on changes and every second. Stop disconnects every stream except the instant switch ones. A pause longer than `LIVE_RESUME` (10 s) reloads the stream on resume, rejoining the live point. While playing, the player reads `qust_audio::info()` every 2 s. The title comes from the stream (ICY or Ogg comments), then the Icecast `status-json.xsl` fallback (at most every 15 s, on a thread of its own, dropped if the station changed meanwhile), then, for a cartridge, the stream's name, then the cartridge or entry name. The views derive what is only presentation: which buttons are enabled, time formatting, a URL's host, the cartridges' and rows' states.

**Streams and instant switch.** What plays is `active()`: the cartridge `cartridges[active_slot]` or the playlist entry `active_entry`, never both. Each source is a stream in the engine under its key (`Entry::key()`: the URL, or `file:` and the path), with `current()` the active one and its `Status`. Keying by URL means reordering cartridges doesn't disturb them.
- **Instant switch** (the ⚡ button, `instant-switch` in the store): every loaded cartridge streams in the background at level 0, even while stopped, so starting or switching is immediate. Only the 6 cartridges preload, never playlist entries, and at most six streams play at once (`MAX_STREAMS`; a playing URL entry takes one). `preload` in each cartridge's state drives the bolt (`loading`, then `live`).
- **`sync_streams()`:** keeps exactly the wanted streams loaded (the active one unless stopped, plus every cartridge in instant mode), reloads background ones that failed or ended, and sets the levels (active 1, others 0). Call it after anything that changes cartridges, the active source or the state.
- **`play()`:** when the target is a stream already being consumed (`status.live`), it switches immediately with no reconnect, and `clock_start` starts the clock from where that stream is. Otherwise it loads it (`connecting`).
- **`pause()`:** pauses only the active stream: its ring fills and the connection backs up behind it. Resuming within `LIVE_RESUME` applies only to the same source (`paused_key`), and only if it hasn't failed or ended. A file (`status.duration` is `Some`) always resumes where it paused.
- **Files** (local, or online with a length): running out of buffer waits (`buffering`) instead of reconnecting, `Ended` plays the next entry, and a reconnect picks up at the same position (`load` with `start_at`). Seeking applies only to a file.

**Reconnecting.** `lost()` runs when the active stream drops: a live stream still out of audio `STALL_TIMEOUT` (3 s) after `Waiting`, `Failed` or `Ended` after it played, or the watchdog. The first try is immediate, then one every second (counted from the previous try's start) for 15 tries, then every 15 s, until `reconnect-minutes` runs out ("Connection lost"). Each try (`reconnect()`) loads the source again under its key, which gives a fresh connection and decoder. A try that isn't playing after 12 s (`ATTEMPT_TIMEOUT`) counts as failed. Playing for 10 s (`RECOVERED_TIMEOUT`) ends the sequence. A source that never played isn't retried: a cartridge stops with "Couldn't play this stream", and a playlist entry is marked `missing` and the next one plays, until every entry has been tried ("Couldn't play this file" or "… stream"). The clock carries over (`clock_base`), and so does the title until the new connection sends one. Background streams that drop are re-synced after 15 s.

**Watchdog.** `watch()` runs every second. If the active stream's time (a file's `position`, a stream's `played`) hasn't moved for 3 s while `playing`, it calls `lost()`, unless no output is running (`Tap::read` gives `None`). Device changes and sleep are the engine's job: it reopens the output by itself, and a stream that doesn't move meanwhile isn't at fault.

**Commands and errors.** Errors from the player are strings, shown as they are (a bad address gets `URL_ERROR`: "Enter an address starting with http:// or https://"). An empty title means the default name: a cartridge's URL host, or an entry's file name without extension (an online file's name, else the host). The cartridge drop animation starts when the move's `Reply` resolves.

**Playlist.** The Playlist button opens the drawer (`PlayerHost::set_drawer`): the app saves `playlist-open` and runs the window animation; the window opens at the saved height. The drawer is mounted as the player window's live layer (`qust_ui_playlist::mount`) in the 860×320 slot the `PlayerView` leaves below itself. The loaded cartridges are pinned at the top of the list: they play and edit there, but move and eject only above. Below them, entries come from:
- dropping files on the window (the drawer watches GPUI's external drags window-wide), added at the drop position, expanded by `playlist::expand`: files, folders (natural name order, recursive) and `.m3u` / `.pls` lists. Lists inside folders are skipped. One drop adds at most 10,000 entries (`MAX_ENTRIES`).
- Add file: the native picker (`qust_shell::picker`) on a thread of its own, then `Drawer::add_paths`, with the same expansion.
- Add URL and Edit… (right-click): the cartridge dialog in URL or entry mode (a local file's path is shown read-only).

The entries live in the player (`Entry` in `model.rs`). Each has an `id` that lasts as long as the app runs and isn't saved; the UI's copy is `models.playlist`. Selection supports Ctrl and Shift, dragging reorders the selection, Delete removes, and Enter or double-click plays. Added entries are selected and revealed. Local files' durations are probed one at a time on another thread (`probe_durations`). A file that can't be opened or isn't audio is marked `missing`. Removing the active entry stops it, and the next one becomes what Play plays. The playlist plays once to the end. For a playlist file with a duration, the volume and balance card shows a seek bar over volume and balance side by side. The state's `duration` is set even while stopped, from the entry's saved duration, so the layout doesn't jump.

**Visualizer.** `visualizer.rs` runs a 60 Hz thread while the player window is attached and the player isn't stopped (while paused, only until the bars have fallen: `Spectrum::idle()`). Each tick reads the engine's `Tap` (the mix before volume, so the bars ignore the volume): `WAVE_LEN` (8192) frames ending `LEAD_SECONDS` ahead of what is heard, output latency included. It runs `Spectrum::tick` with the real time since the last tick and sends the 77-byte frame to the frame sink, only when it differs from the last one sent. `set_loading` follows `connecting` / `buffering`, and `set_off` the `off` colors. On stop it resets the spectrum and sends one all-zero frame. The tap gives silence while nothing plays, so the bars fall. With no output running there is no analysis, and the bars hold still.

The analysis (`qust-spectrum`) is the old page's, ported number for number: the audio is resampled to 44.1 kHz, and a 576-line MDCT (an MP3 granule) folds into 75 columns and 19 bars with falling peaks, at a fixed 60 updates/s. While loading, a row-of-blocks pulse crossfades with the bars (in over 0.2 s, out over 0.5 s). The frame is byte 0, the loader level (0–255), then 4 bytes per bar: `rows` (lit rows from the bottom, 0–15), `peak` (0 = none, else its row), and the loader block's `half` height and `glow` (alpha). With `off`, rows and peaks are 0. `qust_fluent::analyzer` paints it as the page's canvas did: bars at alpha `1 - level` and loader blocks at `level * glow / 255`, in the chosen palette, on a 75×16 pixel grid (3 px bars, 1 px gaps, 16 rows with one color per row), shown at 1:1 and scaled only by whole numbers on high-DPI screens. It is the `analyzer` live layer, so its 60 Hz redraws never re-render the window.

**Background helper.** With `background` on ("Background helper" in Settings, installed copies only), the startup entry runs `qust.exe --background` at sign-in: `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, value `Qust` (plus `StartupApproved`), exactly as the Tauri versions' autostart plugin wrote it.
- **At sign-in:** that launch creates only the tray icon, with GPUI headless (no window, no engine).
- **Closing the player:** the window closes, which detaches the player (`Player::detach`: pending saves are written, playback stops and the engine goes). With the helper on, the process stays in the tray; otherwise it quits. The tray's "Quit Qust" quits.
- **Shortcuts and tray actions:** `background::route` turns them into requests (`play` / `stop` / `toggle`). With no player window, Play and Play / Stop open it and the player plays the last cartridge once it has attached. Stop does nothing.
- **Single instance** (`instance.rs`): the named mutex `<id>-sim` and the hidden window `<id>-sic` / `<id>-siw` that tauri-plugin-single-instance used, with its `WM_COPYDATA` message, so a launch of either version hands over to whichever runs. A plain launch shows the player, and `qust.exe --toggle` acts like Play / Stop. A first launch with `--toggle` opens and plays.
- **Memory:** with the window closed, the idle process holds no window and no audio engine.

**Updates.** `qust-updater` reads `https://github.com/mkpascal/qust/releases/latest/download/latest.json` (the same file the Tauri versions read), takes the entry for its platform (`windows-x86_64-nsis` / `windows-x86_64`, `darwin-<arch>-app` / `darwin-<arch>`), downloads it and checks its minisign signature against `PUBLIC_KEY` (the key the Tauri versions trusted), which must name the announced version in its trusted comment. `qust_shell::updates` keeps the schedule: with "Check automatically" (`auto-update`, on by default), a first check 30 s after launch and then whenever `update-last-check` is 8 hours old. A newer version is downloaded in the background (status `ready`) and installed only when the user clicks "Restart and update" in Settings; a dot on the cog shows that an update is waiting. On Windows the NSIS installer runs passively (`/P /UPDATE /R`), closes Qust and reopens it; on macOS the bundle is replaced and the app restarts itself. Only an installed copy updates (not debug builds, not a copy without `uninstall.exe` next to it).

**Global shortcuts.** `shortcuts.rs` keeps the bindings as accelerators built from key codes (Play `Ctrl+Alt+Insert`, Stop `Ctrl+Alt+KeyH`, Play / Stop unassigned), registered with `RegisterHotKey` on the shell thread. Play / Stop plays when stopped or paused and stops otherwise. It exists so a single Stream Deck "Hotkey" button stays in sync, which a "Hotkey Switch" with separate Play and Stop keys does not. Backspace while recording resets a shortcut to its default, which clears Play / Stop. While Settings records one, the shortcuts are paused (a registered shortcut never reaches the window) and keys are read from the window's messages (`KeyCapture`). Setting a shortcut refuses one another app owns or that another action already uses. Closing Settings always resumes them. A shortcut owned by another app at startup is kept but marked unregistered, and Settings shows it crossed out.

## Debugging and testing

Prefer the headless tests and the examples for anything about audio or the player: they need no window, no sound and no network.

**Windows and captures.** `qust_ui::capture` opens hidden, unfocused, off-screen windows, drives them (`Session::click`, `drag`, `key`, `type_text`…) and reads their pixels with `render_to_image`: nothing appears on screen and no OS input is sent. The capture examples compare against `reference/renders*/` (make them first, see `reference/README.md`); `reference/compare.mjs` reports pixel, region and text differences. Fixtures in `reference/states/` describe each state (what the player sent plus the user's actions), and the window crates' behaviour tests replay `reference/BEHAVIOUR.md`.

**Running the app by hand.** `--settings <file>` keeps the real `settings.json` out of it, and `--null-output` keeps it silent. A debug or `measure` build has its own instance id, so it runs next to an installed Qust in the tray. Global shortcuts owned by an installed Qust show as taken.

The bars must stay identical to the old page's. `tests/reference.rs` in `qust-spectrum` rebuilds synthetic signals sample for sample and compares every frame byte for byte with `tests/reference/frames.txt`, which `tests/reference.mjs` generated from `tests/reference/visualizer.js`, a frozen copy of the page's analyzer from before the port. Never edit that copy. The port mirrors the JS operation by operation in f64, with V8's `sin` / `cos` (`fdlibm.rs`), `Math.round` (`js_round`) and `Math.pow` (`GROWTH`), so don't simplify an expression: rerun the test. The fixture only needs regenerating when the signals change (in both `reference.mjs` and `reference.rs`): `node tests/reference.mjs` in `crates/spectrum`. `ticks_never_allocate` guards the 60 Hz path.

## Gotchas

- **GPUI re-renders the root and every dirty view on each frame, and a notify dirties every ancestor.** Anything that changes often belongs in a live layer (`WindowRoot`), never in the content. Reading a model in `render` doesn't subscribe: always `cx.observe` it. GPUI also refreshes the whole window on activation, pointer enter or leave, bounds and focus changes.
- **Never call GPUI's `window.activate_window()`**: on Windows it injects an Alt key press. Use `qust_shell::window::bring_to_front`.
- **Never show a native menu from inside a GPUI event handler.** Use `qust_shell::menu::popup`: it schedules the menu with a zero timer, so its modal loop runs between two events, and GPUI keeps painting meanwhile (no `TPM_NONOTIFY`, so the owner gets `WM_ENTERMENULOOP`). The choice comes back later through `done`.
- GPUI's text differs from Chromium's: no kerning unless `kern` is asked for, baselines rounded differently for some size pairs, ellipsis, letter spacing. Use `qust_fluent::text` (`font_text`, `font_display`, `type_size`, `spaced_line`, `truncated_line`), never raw text styles. Every title, station name, file name or host shown goes through `qust_text::shown` (right-to-left), but not text boxes, tooltips, menus or the clipboard.
- GPUI rounds authored `px()` lengths but not flex results; exact .5 positions round the other way from Chromium. Margins don't collapse. Content masks are rectangles. An SVG takes no inherited colour. `BoxShadow.blur_radius` is a sigma (half the CSS blur: `paint::css_shadow`). Opacity is per primitive, not per group. Hidden windows get no next-frame callbacks and must be drawn by hand.
- **Debug builds of GPUI compile their shaders at run time** from `vendor/gpui-pre-windows/src/shaders.hlsl`, by the absolute path baked in at build time (release builds embed them). So a debug `qust.exe` only runs next to its source tree, and after moving the repository (or `target/`) the workspace crates and `gpui-pre-windows` must be cleaned (`cargo clean -p …`): Cargo identifies path crates relative to the workspace root and keeps the old builds with the old paths in them (`Creating DirectX renderer` at start).
- **`vendor/gpui-pre-windows`** is GPUI's Windows crate with the right-to-left patch. When GPUI is bumped (`gpui-pre`, `gpui-pre-platform` and `gpui-component` move together, pinned with `=`), re-apply `vendor/gpui-pre-windows.patch` to the new version and replace the copy, or drop both once upstream lays right-to-left runs out itself.
- `MfAacDecoder` holds COM's multithreaded apartment (`CoIncrementMTAUsage`) instead of initializing COM, so it can be created, used, moved and dropped on any thread that isn't a single-threaded apartment. The decode threads are plain `std::thread`s, which are in the implicit MTA. Never create one on a thread that called `CoInitialize` for an STA (GPUI's main thread is one). For the same reason, `output::device_rate()` asks cpal on a thread of its own.
- The rate and channels of decoded audio come from each buffer, never from the codec parameters: HE-AAC switches to twice the announced rate (and to stereo for v2) after the first packets, and `Converter` rebuilds its resampler when the rate changes. After a seek, time is counted in decoded frames from the first packet's timestamp, because the Media Foundation decoder hands out each packet's audio one call late (the first call gives none, and a file's last 23 to 46 ms stays inside).
- On macOS, and on Windows without a system AAC decoder, HE-AAC plays only its LC core (half the rate, no high band). The info still shows the doubled rate from the ADTS header rule.
- `seek()` is ignored until `Duration(Some)` has arrived. To start a file at a position, pass `start_at` to `load()`.
- The engine suppresses events from replaced or unloaded streams, but the player still drops any event whose `StreamId` isn't the current `Status`'s.
- The output closes 3 s after the last stream goes and reopens on the next load. Meanwhile `Tap::read` returns `None`, and nothing is consumed. The mixing rate is fixed when the engine starts.
- A live stream whose server sends no burst can give a `Waiting` right after it starts. That is why a live stream gets `STALL_TIMEOUT` to come back before it reconnects.
- The player thread must never block: `icecast_title` and the duration probes run on threads of their own and report back with `cast`. The UI never waits for the player either: `qust_ui::Player` queues commands on its own thread. `Player::detach` waits for the player, so the player must never wait on the main thread.
- Debug builds optimise every dependency and the audio, codecs, spectrum and player crates at `opt-level = 2` (`Cargo.toml`). Unoptimised, the decoders and resamplers can't keep up with real time. `package."*"` doesn't cover workspace members, so each such crate has its own entry.
- **Instance ids.** Release builds use `com.pascalmuangkhot.qust`, the installed app's, so on a PC where Qust runs in the tray a release build just hands over to it and exits. Debug builds and the `measure` profile (release, with debug assertions in `qust-shell` only) use `com.pascalmuangkhot.qust.debug`. All of them share the installed app's `settings.json` unless given `--settings`.
- Decoders can go over full scale (Opus is unbounded). The tap keeps the overs, as the browser's analyser saw them, and the output clamps.
- The audio extensions are listed four times: `AUDIO_EXTENSIONS` (`crates/player/src/playlist.rs`), `AUDIO_EXTENSIONS` (`crates/ui-player/src/dialog.rs`, for an online file's default name), the picker's filter (`crates/shell/src/picker.rs`) and `audio_type` (`crates/audio/src/info.rs`). Keep them in sync.
- **macOS is best effort and untested.** CI builds it, so the code compiles, but nothing has run there. The shell's macOS side: native menus as NSMenu (`menu_mac.rs`), the menu bar icon as an NSStatusItem (`tray.rs`), global shortcuts with Carbon's `RegisterEventHotKey` (`hotkeys.rs`), the helper as a LaunchAgent (`startup.rs`), the picker through GPUI's open panel, no single-instance lock (`instance.rs`) and no shell thread (`native_other.rs`: calls run on the main thread).
- macOS builds are signed ad hoc, not notarized, so the first launch of a downloaded copy needs right-click → Open.

## Releases and CI

`.github/workflows/build.yml` builds Windows (`cargo build --release`, then the NSIS installer with `packaging/windows/build-installer.mjs`) and macOS (both architectures, combined by `packaging/macos/build-app.sh` into a universal `.app`, `.dmg` and `.app.tar.gz`) on pushes to `main`, pull requests and manual runs, and keeps the files as workflow artifacts. It doesn't run the tests.

To release, bump `version` in `[workspace.package]` in `Cargo.toml` and push to `main`. When no release exists for that version, the `release` job creates a draft "Qust vX.Y.Z". Both builds sign their update file with `qust-sign` (`Qust_<v>_x64-setup.exe`, `Qust_<v>_universal.app.tar.gz`), and the `publish` job writes `latest.json` (`packaging/latest-json.mjs`: each file under both updaters' platform keys, with versioned URLs), uploads everything and makes the release public and latest, so installed copies only ever see a complete release. The installer keeps the Tauri installs' identity (`%LOCALAPPDATA%\Qust`, the `Qust` uninstall key, the startup entry), so it upgrades them in place, and removes the WebView2 cache they left.

Signing needs the repository secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (the names are the Tauri versions'; the key is the same). The key pair lives in `C:\Users\p\.tauri\` (`qust.key`, `qust.key.password`, `qust.key.pub`). If the private key is lost, installed copies can't verify new updates, so it must stay backed up. Local builds don't sign and need no key.
